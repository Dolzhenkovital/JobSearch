# Реєстрація та промокоди

Реалізація від 2026-10-05. В **Administration → Реєстрація** адміністратор перемикає режим:

- **Вільна реєстрація**: новий акаунт створюється без промокоду.
- **Реєстрація за промокодом**: новий акаунт потребує активного коду. Це початковий режим після застосування міграції; початкових кодів немає. Наявні акаунти можуть входити без коду.

Адміністратор створює код із фіксованою кількістю активацій (1–1 000 000) або без обмеження. Код містить 4–64 латинські літери, цифри, дефіс/підкреслення; регістр не має значення. Кожен код можна вимкнути та увімкнути. Після вичерпання ліміту повторне увімкнення не додає активацій; створіть інший код. Зміна коду/ліміту й видалення кодів у цей етап не входять.

Лічильник показує кількість **успішно створених акаунтів**, до підтвердження email. Це не кількість підтверджених або активних користувачів. Видалення акаунта не повертає активацію; його ідентифікатор видаляється з історичного запису. У списку користувачів видно промокод реєстрації. Список кодів і статистика доступні лише серверно перевіреному адміністратору.

Недійсний, вимкнений або вичерпаний код повертає однакове повідомлення «Промокод не активний». Вхід і відновлення пароля наявних акаунтів не витрачають код. Вільний режим не використовує й не враховує коди.

## Серверне забезпечення

`private.registration_settings`, `private.promo_codes` і `private.promo_registrations` закриті від клієнтських ролей. Адмінські операції йдуть через `jobsearch-api`; RPC додатково перевіряють роль. Оновлення режиму/стану коду використовують revision, щоб два адміністратори не перезаписували зміни мовчки.

Тригер `jobsearch_registration` на `auth.users` перевіряє режим, атомарно збільшує лічильник і зберігає зв’язок користувача з кодом у тій самій транзакції, що створює акаунт. Неуспішна транзакція не витрачає активацію. Умова `activations < max_activations` перевіряється під блокуванням рядка, тому остання активація не може бути використана двома одночасними реєстраціями. Тригер діє і для прямих запитів Supabase Auth, адміністративного створення та запрошення нових акаунтів; приховування поля в браузері не обходить обмеження. Наявні користувачі не змінюються. Походження реєстрації береться із приватного запису, а не з метаданих, які може змінити користувач.

Опційний Postgres [Before User Created hook](https://supabase.com/docs/guides/auth/auth-hooks/before-user-created-hook) повертає зрозумілу помилку Auth без створення акаунта. Сам hook не витрачає активацію й не замінює тригер. Клієнт робить попередню перевірку та повторює її при прихованій Auth-помилці тригера; автоматичного повтору створення акаунта немає. Недоступність умов/відсутня міграція блокують кнопку реєстрації, а не вмикають вільний режим.

## Розгортання

1. Для **окремого stage-проєкту Supabase** застосуйте попередні міграції й `supabase/migrations/202610050001_registration.sql` у транзакції. Уже застосовані міграції не запускайте повторно. Після цієї міграції нова реєстрація закрита до створення коду адміністратором. Якщо в новому тестовому проєкті ще немає адміністратора, створіть підтверджений тестовий акаунт і призначте його UUID у `app_admins` **до** застосування цієї міграції.
2. Розгорніть `jobsearch-api` з цієї гілки в той самий stage-проєкт. Якщо доступна CLI-сесія: `supabase functions deploy jobsearch-api --project-ref YOUR_STAGE_PROJECT_REF`.
3. За бажанням увімкніть Authentication → Hooks → Before User Created: Postgres function `public.registration_before_user_created`. Локальна конфігурація hook міститься у `supabase/config.toml`.
4. Задайте GitHub Actions variables `STAGE_VITE_SUPABASE_URL` і `STAGE_VITE_SUPABASE_PUBLISHABLE_KEY`, дозволений Auth Redirect URL `https://dolzhenkovital.github.io/JobSearch/stage/` та `JOBSEARCH_SITE_URL` для stage-функції. Не підключайте stage до production-бази.
5. Злийте feature-PR у `stage`, дочекайтеся Deploy і перевірок після публікації. Pages не застосовує міграції та не розгортає Edge Function.
6. У stage-акаунті адміністратора створіть тестові коди. Перевірте обидва типи, останню активацію в двох незалежних сесіях, відхилення без коду/після вимкнення, лічильник, підтвердження email, вхід наявного акаунта та заборону адмінських дій звичайному користувачу.

Перед наступною промоцією на main міграція й Edge Function мають бути окремо розгорнуті в production. Живі коди та email користувачів не додавайте до репозиторію.

## Межі перевірки

PGlite-тести виконують реальну SQL-міграцію, тригер, права, ліміти й відкат транзакції локально. Модульні/UI-перевірки використовують синтетичні дані. Вони не встановлюють факт живої реєстрації, доставку email або одночасну роботу незалежних PostgreSQL-сесій. У GitHub наразі немає `STAGE_VITE_SUPABASE_*`; stage без цих змінних залишається локальним середовищем без акаунтів. Успішний Pages Deploy не підтверджує підключений stage-бекенд.
