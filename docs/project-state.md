## Ціль продукту

Приватний помічник для однієї кандидатки має скорочувати час від знайденої канадської вакансії до обґрунтованого рішення та перевіреного пакета CV/lettre, а потім зберігати історію заявки на різних пристроях.

Послідовність: **знайти → отримати повний опис → оцінити відповідність → адаптувати документи → перевірити й схвалити → зафіксувати подання та наступні етапи**. Кожен крок має власний результат; створення документа або відкриття зовнішнього посилання не є поданням заявки.

Зафіксовані межі:

- Володіння мовами не використовується для фільтрації, рейтингу, відхилення або onboarding-питань. Мова документа задається окремо.
- Місто, напрями посад, зарплата, графік і дорога ще не надані. Приклади пошуку та значення за замовчуванням не визначають побажань кандидатки.
- Твердження про досвід беруться з наданих документів або підтверджень користувача. Вакансія й AI-чернетка не створюють кандидатських фактів.
- Синхронізація між пристроями потрібна для цільового сценарію; локальна копія забезпечує відновлення й роботу при перебоях.
- За вказівкою користувача 2026-10-02 наступний етап — **оцінка відповідності вакансій та адаптація CV/супровідного листа через зовнішній LLM**. Провайдер, модель, бюджет і доступ ще не визначені.
- Реальні профілі, документи й секрети зберігаються приватно. Публічний репозиторій містить код, інструкції, порожні шаблони та синтетичні перевірки.
- Автоматичне подання, повідомлення роботодавцям, платні сервіси й нові зовнішні автоматизації потребують відповідної вказівки користувача.

## Наступний етап: зовнішній LLM

Користувач визначив цей етап під час аналізу. Мінімальний корисний результат: **збережена вакансія + доказовий профіль → пояснення відповідності через LLM → адаптовані CV/лист → перевірений користувачем пакет**, доступний на його пристроях. Зараз оновлено план і скіли; реалізація та живі виклики — наступна робота.

1. **Підготувати входи.** Повний опис із джерелом/версією, підтримані факти профілю з посиланнями на джерела, відомі побажання та мова документа. Короткі описи дозволяють лише попередню оцінку. Початковий сценарій може користуватися ручним повним описом; автоматичний пошук повного тексту не є обов'язковим перед першою LLM-адаптацією.
2. **Визначити провайдера й підключити приватний adapter.** Узгодити модель, фактичний доступ, бюджет і формат API. Викликати його через серверний/serverless endpoint із перевіркою акаунта; секретний ключ не потрапляє у GitHub Pages, `VITE_` або браузер. Supabase Edge Function — можливий варіант, а не вже прийняте рішення.
3. **Додати доказову LLM-оцінку вакансії.** Вимога → факт/переносний досвід/невідоме/підтверджена суперечність; рішення й готовність до документів окремо. Перевіряти структуровану відповідь і фактичний зміст, зберігати звіт із входами, правилами та provider/model/run. Володіння мовами лишається виключеним з оцінки.
4. **Адаптувати CV та супровідний лист через LLM.** Використовувати підтверджені джерелами факти, повний опис і перевірений звіт; отримувати редаговані тексти, карту доказів і пояснення змін. Зберігати чернетку, не перезаписувати нові правки або подані версії, перевіряти факти й верстку, отримувати окреме схвалення користувача.
5. **Перевірити наскрізний результат і відновлення.** Авторизований обмежений живий виклик, коректний target employer/role, відсутність вигаданих фактів, обробка timeout/rate limit/неправильної відповіді, desktop/mobile UI, синхронізація звітів і пакетів на двох пристроях, ізоляція акаунтів та конфлікти версій. Зафіксувати затримку, використання токенів і фактичну вартість, коли їх надає провайдер.

Результат LLM завжди починається як чернетка. Структурно правильна відповідь, створений DOCX, схвалення користувача й факт подання є окремими доказами. Для обліку подання також потрібно пов'язати повідомлення користувача з конкретним пакетом/файлами; автоматичне надсилання роботодавцю не входить до цього етапу.

Після перевірки першого сценарію вимірювати корисні вакансії, частку з повним описом, дублікати, релевантність відбору за оцінкою кандидатки й час до схваленого пакета. Наявність показників у плані не означає, що їх уже виміряно.

## Як оновлено скіли

Усі п'ять скілів збережено у своїх ролях. `jobsearch-build` отримав карту реалізації, правила перевірки sync і спільний workflow зовнішнього LLM; `sources` — стан фактичного збирача та значення runtime-полів; `profile` — межу між імпортованим текстом і фактами для LLM; `match` — контракт доказової LLM-оцінки; `documents` — контракт адаптації, перевірки та схвалення. Шаблон manifest доповнено приватними посиланнями на знімки, даними LLM-run і доказом конкретного подання.

Скіли не додають функцій застосунку самі. Нові поля шаблону manifest не змінюють поточну схему браузера/Supabase; для її розширення потрібні окремі код, міграція сумісності й перевірки.
