# Адміністрування та зовнішній LLM

Реалізація від 2026-10-02. Інтерфейс адміністратора дає перелік акаунтів із пагінацією, запит на лист відновлення пароля, видалення акаунта з повторним введенням email і налаштування зовнішнього LLM. Роль перевіряється сервером для кожної адмінської дії; адміністраторів не можна видалити через цю панель.

## Налаштування LLM

У **Адміністрування → Зовнішній LLM** задайте:

- **API Base URL** — HTTPS-база провайдера, наприклад `https://api.openai.com/v1`, без `/responses` чи `/chat/completions`.
- **API Key** — зберігається приватно на сервері. Порожнє поле при наступному збереженні залишає попередній ключ; при зміні хоста потрібен новий ключ.
- **Model** — точний ідентифікатор доступної моделі.
- **API Format** — Responses API або Chat Completions. Модель/провайдер мають підтримувати JSON Schema structured outputs.
- **Reasoning Effort** — `default` не надсилає параметр. Інші значення використовуйте лише якщо модель їх підтримує.
- **Monthly Token Budget** — однаковий ліміт окремо для кожного користувача за календарний місяць UTC; `0` означає без обмеження. Враховуються input + output; reasoning уже входить в output.

Перед викликом сервер атомарно резервує консервативну оцінку входу плюс максимальну відповідь. Успішна відповідь уточнює витрати за usage провайдера. При невідомому результаті витрати залишаються рівними резерву; автоматичного повторного платного запиту немає. Той самий request ID повертає збережений стан. Явний новий виклик створює новий ID. Ліміт токенів не є грошовим лімітом рахунку провайдера.

Права адміністратора не відкривають чужі CV/пакети в інтерфейсі. Приватний ключ ніколи не повертається у браузер, навіть адміністратору. Таблиця налаштувань не має клієнтського доступу; це не окреме прикладне шифрування ключа.

## Оцінка та документи

У деталях вакансії є дві явні дії. «Оцінити відповідність» зберігає вимоги, джерела, прямий/переносний досвід, невідомі дані та підтверджені розбіжності. Відсоток є прозорою евристикою за відомими критеріями, поруч показано покриття доказами. Володіння мовами виключено з оцінки й уточнювальних питань. Короткий опис дає лише попередню оцінку.

«Адаптувати CV та лист» потребує CV і повного опису незакритої вакансії. Системний промпт дозволяє змінювати порядок та формулювання лише зі збереженням фактів. Лист має бути конкретним і лаконічним (до 250 слів). Результат містить карту джерел, пояснення змін і питання для перевірки. Структурна валідація та перевірка чисел не доводять правдивості всіх перефразувань: факти й верстку перевіряє користувач.

Збереження створює новий несхвалений пакет і за потреби додає вакансію до обліку заявок. Оригінальні CV, правки та подані версії не перезаписуються. Зміни входів позначають попередню оцінку/чернетку як застарілу. Серверна історія містить знімки входів, модель, версію правил і usage; пакет містить посилання `llmRunId`. JSON-резервна копія робочого простору включає тексти пакетів, але не окремі таблиці історії LLM.

Натискання AI-кнопки передає текст профілю/CV та вакансії налаштованому провайдеру. Окремі контактні поля не додаються до запиту; контакти, уже вписані у текст CV, можуть бути в ньому. Перед роботою з реальним CV враховуйте політику обраного провайдера. Налаштування провайдера не створює його облікового запису й не купує кредити.

## Розгортання

1. Застосуйте `supabase/migrations/202610020001_admin_llm.sql` після міграції workspace. При ручному запуску виконайте її в транзакції. Для нового середовища не запускайте повторно вже застосовану міграцію.
2. Призначте потрібний **підтверджений** Auth UUID у `public.app_admins` через довірений SQL/адмінський канал. Реальні email/UUID не додавайте в Git. Немає клієнтського способу самопризначення ролі.
3. Розгорніть `supabase/functions/jobsearch-api/index.ts` через Supabase CLI: `supabase functions deploy jobsearch-api --project-ref YOUR_PROJECT_REF`. `supabase/config.toml` вимикає legacy JWT gateway check; кожний запит усе одно перевіряється через `auth.getUser` у функції, а адмінські дії — за DB-роллю. Це необхідно для сумісності з асиметричними signing keys.
4. Runtime автоматично надає `SUPABASE_URL` та `SUPABASE_SERVICE_ROLE_KEY`. За потреби задайте `JOBSEARCH_SITE_URL` і `JOBSEARCH_ALLOWED_ORIGINS` (список origins через кому). За замовчуванням використовується поточний GitHub Pages сайт.
5. Налаштуйте Auth Site URL/Redirect URL і поштову доставку. Кнопка відновлення використовує Supabase recovery email; новий пароль вводить користувач після переходу за посиланням. Стандартна пошта Supabase має обмеження адресатів/частоти, тому для звичайних зареєстрованих користувачів потрібен власний SMTP. Успішний API-запит ще не доводить отримання листа.
6. Опублікуйте клієнт через наявний Pages workflow. У клієнтську збірку входять лише публічні Supabase URL/key. Секрети провайдера вводяться через захищену адмінпанель після входу.

Офіційні контракти: [Supabase recovery](https://supabase.com/docs/reference/javascript/auth-resetpasswordforemail), [SMTP](https://supabase.com/docs/guides/auth/auth-smtp), [OpenAI structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs), [reasoning](https://developers.openai.com/api/docs/guides/reasoning).

## Перевірки 2026-10-02

- 41 TypeScript/Vitest-тест: доменні правила, RLS/права й бюджет у PGlite, безпека API, синхронізація, форми та підтвердження видалення.
- 3 Python-тести збирача; успішні TypeScript/Vite build та Deno type check.
- Нові панелі візуально перевірено в браузері на desktop та 390×844 із синтетичними даними. Фізичний телефон цим не перевірено.
- У живій базі створено таблиці/функції, призначено запитану роль підтвердженому акаунту; перевірка прав показала відмову доступу anon/authenticated до секретного RPC і заборону прямого запису LLM-результатів.
- `jobsearch-api` розгорнуто в Supabase; неавторизований HTTP-запит до працюючої функції повернув `401 authentication_required`. Legacy JWT gateway вимкнено, перевірку користувача виконує код функції.
- Провайдер, модель і ключ ще не налаштовані. Платні LLM-виклики, реальна доставка recovery-листа, видалення реального акаунта й синхронізація AI-пакета між фізичними пристроями не перевірялися.

Для оновлень промптів змінюйте `RULES_VERSION`; не переінтерпретовуйте історичні результати як згенеровані новими правилами.
