# Реєстрація та промокоди

Реалізація від 2026-10-05. В **Administration → Реєстрація** адміністратор перемикає режим:

- **Вільна реєстрація**: новий акаунт створюється без промокоду.
- **Реєстрація за промокодом**: новий акаунт потребує активного коду. Це початковий режим після застосування міграції; початкових кодів немає. Наявні акаунти можуть входити без коду.

Адміністратор створює код із фіксованою кількістю активацій (1–1 000 000) або без обмеження. Код містить 4–64 латинські літери, цифри, дефіс/підкреслення; регістр не має значення. Кожен код можна вимкнути та увімкнути. Після вичерпання ліміту повторне увімкнення не додає активацій; створіть інший код. Зміна коду/ліміту й видалення кодів у цей етап не входять.

Лічильник показує кількість **успішно створених акаунтів**, до підтвердження email. Це не кількість підтверджених або активних користувачів. Видалення акаунта не повертає активацію; його ідентифікатор видаляється з історичного запису. У списку користувачів видно промокод реєстрації. Список кодів і статистика доступні лише серверно перевіреному адміністратору.

Недійсний, вимкнений або вичерпаний код повертає однакове повідомлення «Промокод не активний». Вхід і відновлення пароля наявних акаунтів не витрачають код. Вільний режим не використовує й не враховує коди.

## Серверне забезпечення

`private.registration_settings`, `private.promo_codes` і `private.promo_registrations` закриті від клієнтських ролей. Адмінські операції йдуть через `jobsearch-api`; RPC додатково перевіряють роль. Оновлення режиму/стану коду використовують revision, щоб два адміністратори не перезаписували зміни мовчки.

Тригер `jobsearch_registration` на `auth.users` перевіряє режим, атомарно збільшує лічильник і зберігає зв’язок користувача з кодом у тій самій транзакції, що створює акаунт. Неуспішна транзакція не витрачає активацію. Умова `activations < max_activations` перевіряється під блокуванням рядка, тому остання активація не може бути використана двома одночасними реєстраціями. Тригер діє і для прямих запитів Supabase Auth, адміністративного створення та запрошення нових акаунтів; приховування поля в браузері не обходить обмеження. Наявні користувачі не змінюються. Походження реєстрації береться із приватного запису, а не з метаданих, які може змінити користувач.

Postgres [Before User Created hook](https://supabase.com/docs/guides/auth/auth-hooks/before-user-created-hook) повертає зрозумілу помилку Auth без створення акаунта. Сам hook не витрачає активацію й не замінює тригер; навіть без hook тригер закриває реєстрацію. Публічний RPC `registration_mode()` повертає **лише режим**, без перевірки довільних кодів. Перевірка коду відбувається лише під час Auth signup, з обмеженнями частоти Supabase Auth. Supabase приховує помилки тригерів: при такій помилці клієнт повідомляє про серверний збій і можливу втрату активації після hook, не стверджуючи, що причина точно в коді. Автоматичного повтору створення акаунта немає. Недоступність режиму/відсутня міграція блокують кнопку реєстрації, а не вмикають вільний режим.

Тригер змінює лише приватні записи й не перезаписує Auth metadata. Користувач може змінити власні metadata, але адмінський список читає історичний приватний зв’язок. Service-role ключ є довіреною серверною межею: RPC доступні тільки цій ролі; `jobsearch-api` підставляє перевірений Auth UUID, а SQL перевіряє його роль. Власник service-role ключа має повні серверні повноваження, тому його не можна передавати браузеру чи іншим недовіреним клієнтам.

## Розгортання

1. Для **окремого stage-проєкту Supabase** застосуйте попередні міграції й `supabase/migrations/202610050001_registration.sql` у транзакції. Уже застосовані міграції не запускайте повторно. Після цієї міграції нова реєстрація закрита до створення коду адміністратором. Якщо в новому тестовому проєкті ще немає адміністратора, створіть підтверджений тестовий акаунт і призначте його UUID у `app_admins` **до** застосування цієї міграції.
2. Розгорніть `jobsearch-api` з цієї гілки в той самий stage-проєкт. Якщо доступна CLI-сесія: `supabase functions deploy jobsearch-api --project-ref YOUR_STAGE_PROJECT_REF`.
3. Увімкніть Authentication → Hooks → Before User Created: Postgres function `public.registration_before_user_created`. Локальна конфігурація hook міститься у `supabase/config.toml`.
4. Задайте GitHub Actions variables `STAGE_VITE_SUPABASE_URL` і `STAGE_VITE_SUPABASE_PUBLISHABLE_KEY`, дозволений Auth Redirect URL `https://dolzhenkovital.github.io/JobSearch/stage/` та `JOBSEARCH_SITE_URL` для stage-функції. Не підключайте stage до production-бази.
5. Злийте feature-PR у `stage`, дочекайтеся Deploy і перевірок після публікації. Pages не застосовує міграції та не розгортає Edge Function.
6. У stage-акаунті адміністратора створіть тестові коди. Перевірте обидва типи, останню активацію в двох незалежних сесіях, відхилення без коду/після вимкнення, лічильник, підтвердження email, вхід наявного акаунта та заборону адмінських дій звичайному користувачу.

Для відкату UI/Edge Function поверніть попередній перевірений реліз; SQL-лічильники й історію збережіть. Повернення старого UI не прибирає Auth-тригер і не відкриває реєстрацію. Режим можна змінити існуючим підтвердженим адміністратором через серверний RPC з поточною revision; не видаляйте приватні таблиці для обходу невдалого деплою.

Перед наступною промоцією на main міграція й Edge Function мають бути окремо розгорнуті в production. Живі коди та email користувачів не додавайте до репозиторію.

## Межі перевірки

Актуальні датовані live-перевірки SMTP, AI та підготовки production наведені в [журналі релізу 2026-10-08](release-2026-10-08.md). Наведені нижче обмеження попередніх перевірок описують стан на момент тих перевірок.

PGlite-тести виконують реальну SQL-міграцію, тригер, права, ліміти й відкат транзакції локально. Модульні/UI-перевірки та браузерний smoke-тест реєстрації використовують синтетичні дані. Вони не встановлюють факт живої реєстрації, доставку email або одночасну роботу незалежних PostgreSQL-сесій.

Міграцію також перевірено на живому stage PostgreSQL усередині транзакції з повним `ROLLBACK`: відхилення без коду, ліміт одного акаунта, необмежений код, вимкнення, вільний режим і права RPC. Це перевірка бази, а не HTTP Auth signup чи email.

2026-10-05 створено окремий **JobSearch Stage** у Canada Central, налаштовано GitHub `STAGE_VITE_SUPABASE_*` і Auth Site/Redirect URL `/JobSearch/stage/`. Усі три міграції застосовано, stage `jobsearch-api` розгорнуто й Before User Created hook увімкнено. Живі HTTP-перевірки підтвердили: режим `promo`, відсутній публічний RPC перевірки кодів (404), Auth signup із неактивним синтетичним кодом відхиляється з 400 `promo_code_inactive`, функція без токена повертає 401 `authentication_required`. Перший підтверджений stage-акаунт існує; надання йому адмінської ролі очікує підтвердження користувача. Перевірка автентифікованого UI, успішного signup/email та конкуренції незалежних сесій ще потрібна. Production-бекенд не змінено.

2026-10-08 підтверджено автентифікований stage UI адміністратора та створення обох типів кодів. Живий Auth signup витратив одну активацію до підтвердження email; лист на тестову адресу власника доставлено, підтвердження відкрило звичайний акаунт без адміністративного UI та без даних іншого користувача. Наступний signup із вичерпаним кодом відхилено з `promo_code_inactive`. Два незалежні SQL-запити з перекриттям транзакцій використали останню активацію лише один раз; це перевірка PostgreSQL, а не одночасної HTTP-реєстрації. Необмежений код, його вимкнення, вільний режим і приватні права перевірено з `ROLLBACK`. Власний SMTP на stage вимкнений; наступний Auth signup отримав `429 over_email_send_rate_limit`, тому повний HTTP-сценарій необмеженого коду ще не завершено. Для реєстрації громади потрібен [власний SMTP](https://supabase.com/docs/guides/auth/auth-smtp).

Два реальні виклики stage LLM (оцінка та адаптація) через Responses API успішно використали 3 123 токени. Оцінка розділила підтверджений досвід та невідомий сертифікат, виключила мову; документи залишилися чернеткою з джерелами. Тестовий простір відновлено з попередньої копії через revision-checked RPC. Перевірки lint/typecheck, 126 unit-тестів, 3 Python-тести та всі 10 desktop/mobile smoke-тестів пройшли. Production `registration_mode()` повертав 404: міграція, актуальна Edge Function і Auth hook мають бути розгорнуті до промоції. Merge на main не виконується до закриття поштової перевірки й підготовки production-бекенду.

`verify_workspace.sql` пройшов на живому stage після міграції: запис власника, відхилення застарілої revision, ізоляція іншого акаунта й заборона анонімного доступу. Скрипт тимчасово відкриває реєстрацію лише всередині тестової транзакції; `ROLLBACK` повертає режим і прибирає синтетичні записи. Перевірка двох фізичних пристроїв окремо не виконувалася.

Компоненти перевіреного stage: UI commit `463dcddd9db3c0cfc0581bffcf28062863eaa5b3`, міграції `202610010001_workspace.sql`, `202610020001_admin_llm.sql`, `202610050001_registration.sql`, вручну розгорнута `jobsearch-api` та hook `public.registration_before_user_created`. Функція не публікує commit marker, тому його не можна звірити з UI marker. Для повторення cloud-перевірки спочатку виконайте ручні кроки з [розділу «Розгортання»](#розгортання); CI застосовує лише вебзбірку. Тестові коди після QA вимкнено; SMTP у stage та production на момент перевірки вимкнений.
